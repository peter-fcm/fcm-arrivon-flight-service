# Agent Guidelines: FCM Arrivon Flight Service

This document provides persistent architectural and coding guidelines for AI agents working in this repository.

---

## 1. Project Context & Environment
- **Project**: `fcm-arrivon-flight-service`
- **Language**: Java 25 (Object-Oriented Programming)
- **Framework**: Spring Boot
- **Build Tool**: Maven (wrapper `./mvnw`)

---

## 2. Core Object-Oriented Principles & Clean Code

- **Object-Oriented Principles**:
  - Always adhere to OOP fundamentals and clean code principles: **SOLID**, **DRY** (Don't Repeat Yourself), and **KISS** (Keep It Simple, Stupid).
- **Abstractions & Decoupling**:
  - Use abstractions such as **Interfaces** and **Dependency Injection** to enhance code maintainability, loose coupling, and testability.
- **Strict Encapsulation**:
  - Methods must **never** be set to `protected` (or package-private) merely to make them accessible for unit tests. Test behaviors through public contracts or refactor into dedicated injectable components.
- **Coding Style & Naming Standards**:
  - An imperative coding style (reminiscent of C or Python) is **strictly forbidden**.
  - Follow idiomatic, object-oriented Java conventions.
  - Variable and method names must be fully spelled out and clearly descriptive.
  - **No abbreviations** in method, class, or variable names (e.g., use `flightRepository` not `repo`, `destinationAirport` not `destApt`).

---

## 3. Java 25 Best Practices & Modern Language Features

- **Prefer Records for Data Carriers**:
  - Use `record` for all DTOs, query/command payloads, event objects, and projection classes.
  - Rely on record immutability, built-in accessors, and canonical constructors.
- **Pattern Matching & Modern Constructs**:
  - Utilize pattern matching for `instanceof` and modern `switch` expressions/statements with exhaustiveness checking.
  - Utilize sealed classes/interfaces when modeling closed hierarchies (e.g., flight status states, domain events, result types).
- **String Templates & Text Blocks**:
  - Prefer multiline text blocks (`""" ... """`) for formatted text, SQL, JSON, or XML snippets rather than concatenations.
- **Collection Factories & Immutability**:
  - Default to unmodifiable collections (`List.of()`, `Set.of()`, `Map.of()`, or `stream().toList()`).
  - Treat services and components as stateless: keep all fields `private final` and avoid mutable shared state.

---

## 4. Spring Ecosystem & Dependency Injection

- **Leverage the Spring Ecosystem**:
  - Maximize the use of the Spring ecosystem for dependency injection, component lifecycle management, and application infrastructure.
- **Constructor Injection Only**:
  - Never use field injection (`@Autowired` on private fields).
  - Use constructor injection for all required dependencies (either via explicit constructor or Lombok's `@RequiredArgsConstructor`).
- **Configuration & Properties**:
  - Bind external configuration using `@ConfigurationProperties` with immutable record classes.
  - Keep configuration classes separated from application business logic.
- **Lombok Usage**:
  - Use Lombok purposefully:
    - `@RequiredArgsConstructor` for constructor dependency injection.
    - `@Getter` / `@ToString` if traditional classes are unavoidable.
    - Prefer Java `record` over `@Data` or `@Value` for data carriers and DTOs.

---

## 5. Testing Conventions

- **Mocking Restrictions**:
  - Mocking is **strictly prohibited in production code**; it is only allowed within test classes.
- **Controller Testing**:
  - Test Controllers using **MockMvc** (e.g., via `@WebMvcTest`).
- **Spring Test Integration**:
  - Leverage Spring's test support infrastructure and slicing annotations for integration and unit testing.

---

## 6. Code Quality & IntelliJ Code Analysis Verification

- **Mandatory IntelliJ Code Analysis**:
  - **Before considering any task or change complete, always read the code analysis generated by IntelliJ** (using IntelliJ inspections / tools such as `lint_files` or `get_file_problems`).
  - Inspect any modified and affected files for errors, warnings, and code smells.
  - Resolve or address detected issues (such as unused variables, dead code, redundant null checks, or syntax/type warnings) before concluding the task.

---

## 7. Verification & Workflow Commands

Before concluding tasks or submitting changes, verify that the project compiles, tests pass, and IntelliJ code analysis has been reviewed:

```bash
# Compile and run tests
./mvnw clean test

# Quick compilation check
./mvnw test-compile
```
